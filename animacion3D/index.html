Dos depósitos concurrentes

Dos hilos intentan depositar 100 cada uno en el mismo saldo. Ejecuta la simulación para ver qué ocurre.

Cada depósito es leer, sumar y escribir. Son tres pasos separados.

Si las operaciones se intercalan, el resultado puede ser incorrecto.

Aplicación y memoria compartida. Todavía no hay mutex ni intervención del kernel.

Código y caso límite

La operación saldo += 100 no es atómica: primero se lee el saldo, luego se suma y finalmente se escribe. 

// el mismo saldo para los dos hilos
long saldo = 1000;

    La idea central

    Leer y escribir no ocurre en un solo instante

    Cada operación sobre el saldo son varios pasos. Si dos hilos intercalan esos pasos, el estado compartido termina siendo distinto del esperado. A esto se le llama condición de carrera.

    01

    Leer

    El hilo copia el saldo actual en su propio registro.

    02

    Calcular

    Suma 100 usando la copia que leyó, no el saldo real.

    03

    Escribir

    Guarda el resultado y puede sobrescribir el de otro hilo.

    Resumen del módulo

    Tres ideas para llevarte

    1. 01
      Recurso compartido

      Un archivo, una tabla o un saldo puede ser leído y modificado por varios hilos.

    2. 02
      Acciones intercaladas

      Si dos hilos leen antes de escribir, el segundo write puede borrar el primero.

    3. 03
      Reglas de sincronización

      La solución empieza por proteger la sección crítica; el mutex es la siguiente pieza.
